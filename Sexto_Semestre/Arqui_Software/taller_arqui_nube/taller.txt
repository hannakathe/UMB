SAAM (Software Architecture Analysis Method)
Es uno de los primeros métodos formales creados por el SEI (Software Engineering Institute) para evaluar arquitecturas de software. Nació en los años 90 con un enfoque principal: evaluar la modificabilidad de un sistema.

¿Cómo funciona? Se basa puramente en escenarios. Los stakeholders (desarrolladores, usuarios, administradores) proponen situaciones hipotéticas de cambio (ej. "¿Qué pasa si cambiamos la base de datos de Oracle a PostgreSQL?").

El Proceso: Se toma la arquitectura propuesta y se "simula" el impacto de cada escenario. Se cuentan cuántos componentes tendrían que modificarse para lograr el cambio.

El Veredicto: Si un escenario requiere cambios masivos en todo el sistema, la arquitectura es rígida. Si el impacto está aislado en un solo módulo, la arquitectura tiene alta modificabilidad.

Limitación: SAAM es excelente para la modificabilidad, pero se queda corto cuando hay que analizar el rendimiento o la seguridad al mismo tiempo.

ATAM (Architecture Tradeoff Analysis Method)
ATAM es la evolución directa de SAAM, también desarrollado por el SEI. Es el estándar de oro en la industria porque comprende que en la arquitectura moderna no se puede tener todo perfecto al mismo tiempo. Mejorar un atributo (ej. máxima seguridad con encriptación pesada) casi siempre empeora otro (ej. el rendimiento bajará).

¿Cómo funciona? Evalúa las decisiones arquitectónicas frente a múltiples atributos de calidad (Rendimiento, Disponibilidad, Seguridad, Modificabilidad) y busca los Trade-offs (puntos de compromiso o sacrificio).

Artefactos clave:

Árbol de Utilidad (Utility Tree): Una estructura jerárquica donde se priorizan los atributos de calidad más críticos para el negocio.

Puntos de Sensibilidad: Decisiones arquitectónicas que afectan drásticamente a un atributo (ej. "Usar un balanceador de carga mejora la disponibilidad").

Puntos de Trade-off: Decisiones que afectan a más de un atributo, mejorando uno pero perjudicando otro (ej. "Aumentar el nivel de loggeo mejora la auditabilidad, pero reduce el rendimiento").

Riesgos: Decisiones que podrían causar que el sistema no cumpla con sus requerimientos.

ATAM no te dice si una arquitectura es "buena" o "mala". Te dice si la arquitectura es adecuada para los objetivos de negocio específicos de ese proyecto, basándose en los sacrificios que estás dispuesto a hacer.

Heurísticas de Nielsen (Evaluación Heurística)
Mientras ATAM evalúa el código y los servidores, Jakob Nielsen (el padre de la usabilidad web) creó en 1994 un conjunto de 10 principios generales para el diseño de interacción. Son "heurísticas" porque son reglas generales basadas en la experiencia, no leyes matemáticas rígidas. Sirven para evaluar la Usabilidad de una interfaz sin necesidad de hacer costosas pruebas con usuarios reales de inmediato. Las 10 reglas son:

Visibilidad del estado del sistema: El usuario siempre debe saber qué está pasando (ej. Barras de carga).

Relación entre el sistema y el mundo real: Usar lenguaje y conceptos familiares para el usuario, no jerga técnica (ej. El ícono de un bote de basura para eliminar).

Control y libertad del usuario: Ofrecer siempre una "salida de emergencia" (ej. Botón de "Deshacer" o "Cancelar").

Consistencia y estándares: No obligar al usuario a adivinar si diferentes palabras o acciones significan lo mismo.

Prevención de errores: Es mejor un diseño que impida el error antes de que ocurra (ej. Deshabilitar el botón "Enviar" hasta que todos los campos obligatorios estén llenos).

Reconocer antes que recordar: Hacer visibles los objetos, acciones y opciones (ej. Autocompletado en un buscador).

Flexibilidad y eficiencia de uso: Atajos para usuarios expertos que no estorben a los novatos (ej. Comandos de teclado como Ctrl+C).

Diseño estético y minimalista: Los diálogos no deben contener información irrelevante que compita con la importante.

Ayudar a los usuarios a reconocer, diagnosticar y recuperarse de errores: Mensajes de error en lenguaje claro, indicando el problema y la solución constructiva.

Ayuda y documentación: Aunque el sistema debe ser intuitivo, a veces es necesaria documentación fácil de buscar y enfocada en las tareas del usuario.

1. Diagrama del Monolito: "El Bloque Unido"
Patrón: Arquitectura en Capas (Layered Architecture).

Cómo dibujarlo:

Capa de Presentación (UI)
index.html, CSS, JavaScript.

El navegador del usuario vive aquí.

Capa de Lógica de Negocio (Business Logic)
El "Cerebro". Aquí van las reglas:

* UserService (Registrar, Login)

* EventService (Listar eventos)

* OrderService (Crear orden, comprar entrada)

* PaymentService (Procesar pago)

Capa de Acceso a Datos (DAL)
El "Cartero". Habla con la base de datos.

* UserDAO (CRUD de Usuarios)

* EventDAO (CRUD de Eventos)

* OrderDAO (CRUD de Órdenes)

Base de Datos (Monolítica)
Una sola base de datos SQL gigante con todas las tablas:

Users, Events, Orders, Payments, etc.

Beneficio: Estamos separando la lógica de negocio de la presentación, lo que "facilita la reutilización del código".

Problema (El NFR): ¿Qué pasa cuando hay un pico de tráfico para comprar entradas? EXPLIQUE...

La OrderService consume el 99% del CPU.

Todo el monolito se vuelve lento: el login, la lista de eventos... todo.

El Atributo Crítico Afectado: No podemos escalar solo la OrderService. Tenemos que escalar la aplicación entera. Esto afecta críticamente la Escalabilidad.

2. El Pipeline de CI/CD (DevOps)
Esto automatiza las pruebas. GitHub lo detecta automáticamente.

Crea una carpeta llamada: .github

Dentro de esa carpeta, crea otra llamada: workflows

Dentro de workflows, crea un archivo llamado: ci.yml

YAML
# Archivo: .github/workflows/ci.yml

name: Taller CI Pipeline # Nombre del pipeline

on:
  push: # Se activa con CADA push (commit)
    branches: [ "main" ] # Solo en la rama principal
  workflow_dispatch: # Permite iniciarlo manualmente

jobs:
  # 1. El trabajo de "Construcción" (Build)
  build:
    runs-on: ubuntu-latest # Se ejecuta en una máquina virtual de Linux

    steps:
      - name: 1. Checkout del código
        uses: actions/checkout@v4 # Acción oficial para descargar el código del repo

      - name: 2. Simular una construcción (Build)
        run: echo "Construyendo el proyecto... (aquí iría 'npm run build', etc.)"

      - name: 3. Simular guardado de artefacto
        run: |
          mkdir -p build
          cp index.html build/
          echo "Archivos 'construidos' movidos a la carpeta /build"

  # 2. El trabajo de "Pruebas" (Test)
  test:
    needs: build # Este trabajo NO empieza hasta que 'build' termine
    runs-on: ubuntu-latest

    steps:
      - name: 1. Checkout del código
        uses: actions/checkout@v4

      - name: 2. Simular pruebas (Linting)
        run: |
          echo "Ejecutando pruebas..."
          # Simulación de una prueba que busca la palabra "Rock"
          grep -q "Rock" index.html
          echo "Prueba de 'Linting' pasada."

      - name: 3. Simular pruebas de unidad (Unit Test)
        run: |
          echo "Ejecutando pruebas de unidad..."
          # Simulación de una prueba que busca el copyright
          grep -q "EventFlow" index.html
          echo "Prueba de 'Copyright' pasada."
          
      - name: 4. ¡Despliegue simulado!
        run: echo "¡Pruebas exitosas! Listo para desplegar."
